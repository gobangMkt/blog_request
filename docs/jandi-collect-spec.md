# 잔디 결제 알림 가져오기 설계 (jandi-collect-spec)

작성 11.24, 개발팀장 관점. 상태 = 3.5단계 승인(11-3) 뒤 슬라이스 1~7을 코드·node 시험까지 구현했다(11.24). GAS 재배포·앱 푸시는 11.24 끝났고 실제 잔디 탭 북마크 실행은 미확인이다(11-7절). 아래 1~10절은 설계 당시 문장이고, 20897 정정은 11-4절, 실측은 11-5절이 우선한다.
대상 = `addon-direct-pay/paste.html` + `gas-code/Code.gs` (구조 정본은 `addon-direct-pay/README.md`).
근거 = 위 두 파일, `docs/design-system.md`, 개발팀장 기준(`에이전트/service-master/context/domains/dev/` 의 engineering_principles·integration_data·architecture_ops), 11.24 잔디 방 실측.
확정된 운영 조건: ① 사용자는 마케팅팀 2명(토미, 스티브)뿐이고 둘 다 크롬과 잔디 계정이 있다. ② 이미지 건(토스 알림톡 캡처)은 이번 범위에서 제외로 확정이다. ③ 신청 내역 시트의 열 구조는 바꿀 수 없다(기존 GAS 3개·어드민·CS앱이 쓴다).
읽지 못한 것(= 미확인): 잔디 화면의 메시지 고유 ID 속성, 잔디 화면 보안 정책(CSP), 잔디 약관, 저장소 밖에 따로 붙어 있을 수 있는 시트 바인딩 스크립트·수식(4-4).

## 1. 한 줄 결론과 추천 구조

**잔디 방을 읽는 일은 "누르는 사람 본인의 크롬"에서 하고, 시트와 맞춰 보고 등록하는 일은 지금의 `paste.html`과 GAS가 한다. 사용자가 2명뿐이라 읽기는 북마크릿(크롬 북마크 한 줄)으로 시작하고, 스토어 게시나 별도 인프라는 만들지 않는다.**

```
[잔디 방 탭]  북마크 "결제 가져오기" 클릭
   -> 화면을 위로 스크롤하며 결제 후보 글만 모음 (이 탭의 로그인 그대로)
   -> paste.html 새 창을 열고 후보 원문 + 읽기 결과(건수)를 postMessage로 전달
[paste.html]  GAS previewJandi (읽기 전용 대조)
   -> 대조 카드: 읽은 N / 이미 있음 N / 새로 등록 N / 확인 필요 N
   -> 확인 팝업 -> GAS importJandi (등록, 잠금, 중복 방지)
   -> 고급형은 지금 있는 전화번호 입력 카드, 빌리투어는 같은 파일의 새 시트 탭에 쌓기(신청 내역 시트에는 섞지 않음)
```

핵심 판단 3개:
1. 놓침을 막는 힘의 대부분은 "읽기 자동화"가 아니라 "시트와 대조해서 빈 건을 드러내는 것"에서 나온다. 이번에 누락된 20897(11.06 10:01 고급형)은 대조만 있어도 잡힌다.
2. 파서는 GAS 한 곳에만 둔다(정본 1개). 북마크릿은 읽기만 하고 판정하지 않는다.
3. 못 읽은 건은 조용히 버리지 않고 "확인 필요" 목록으로 보내 상태로 남긴다.

## 2. 누가 어디서 로그인하나

**직답: 토미 로컬도 아니고, 배포한 사람도 아니다. 버튼을 누르는 사람(토미 또는 스티브) 본인이 자기 크롬에서 자기 잔디 계정으로 로그인한 상태여야 한다. 사용자는 이 2명뿐이다.**
- `paste.html`은 GitHub Pages의 정적 페이지다. 브라우저 같은 사이트 정책 때문에 잔디 화면을 직접 읽을 수 없고, 로그인도 대신 못 한다.
- 그래서 읽는 코드는 잔디 탭 안에서 돌아야 한다(북마크릿 또는 확장). 로그인 토큰을 꺼내 쓰는 방식은 쓰지 않는다.
- 전제: 두 사람 모두 그 잔디 방(방 id 35912598) 멤버여야 한다. 둘 다 잔디 계정이 있다는 것은 확정이고, 방 멤버 여부는 각자 방을 열어 보면 바로 확인된다.
- 토미 PC는 개발·시험에만 쓴다. 운영 때 토미 PC가 켜져 있을 필요는 없다.

설치 부담은 2대 기준으로 비교한다.

| 구분 | A 크롬 확장(압축해제 설치) | B 북마크릿 | C 서버 공용 계정 긁기 |
|---|---|---|---|
| 로그인 주체 | 누르는 사람 본인 | 누르는 사람 본인 | 서버에 맡긴 공용 계정(비밀번호 또는 토큰을 서버가 보관) |
| 설치 부담(2대) | 2대에 각 1회: 폴더를 받아 크롬 확장 화면에서 개발자 모드를 켜고 폴더 지정. 폴더를 지우거나 옮기면 꺼짐. 크롬이 개발자 모드 확장을 경고·비활성화할 수 있음(미확인) | 2대에 각 1회: 북마크 한 줄을 북마크바에 끌어다 놓기 | 설치 0. 대신 상시 도는 브라우저 서버를 개발·운영해야 함 |
| 깨질 때 | 잔디 화면이 바뀌면 깨짐. 고치면 2대에서 각각 폴더 교체 후 새로고침 | 잔디 화면이 바뀌면 깨짐. 고치면 2대에서 각각 북마크 교체(2대라 로더 방식이 필요 없고, 잔디 보안 정책에 막힐 걱정도 피한다) | 로그인 만료·2차 인증·봇 차단에 걸리면 아무도 모르게 멈춤 |
| 보안·약관 위험 | 권한을 잔디·`paste.html` 두 주소로 한정 가능. 약관 미확인 | 별도 권한 없음, 누를 때만 실행. 약관 미확인 | 가장 큼. 공용 계정 자격 보관, 자동 로그인은 약관 위반 가능성(미확인), 토큰 빼내기 불채택 원칙과 충돌 |
| 놓침 방지력 | 높음. 잔디 화면에 버튼이 떠 있고 "오늘 안 눌렀음" 표시도 가능 | 중간. 사람이 눌러야 함. 대조 화면이 보완 | 이론상 최고, 조용히 멈추면 최악 |

**판단: 2명이면 북마크릿으로도, 압축해제 확장으로도 충분하다. 설치 인프라(스토어 게시, 로더, 자동 업데이트)는 필요 없다. 추천은 B 북마크릿 먼저, 잔디 화면 읽기 시험(슬라이스 1)에서 막히거나 두 사람이 불편해하면 A 압축해제 확장으로 간다. C는 하지 않는다.**
- 비용 0, 심사 없음, 설치 1분. 2명에게는 적정기술이다(개발 원칙 2번: 적정기술 > 트렌디한 기술).
- A를 먼저 택하지 않는 이유: 확장의 장점(상시 버튼)은 쓸 만하지만 개발자 모드 경고·폴더 보관이라는 관리 부담이 생기고, 읽기 방식이 검증되기 전에 만들 이유가 없다. 읽기 로직은 같은 코드라 나중에 A로 옮기는 비용이 작다.
- 인원이 늘면(3명 이상) 그때 스토어 비공개 게시를 다시 검토한다. 지금은 범위 밖.

**버튼 위치: 가져오기 버튼은 잔디 화면에, 결과·등록 버튼은 `paste.html`에 둔다.**
- 읽기는 화면에 떠 있는 잔디 탭이어야 한다. 백그라운드 탭은 브라우저가 타이머·화면 갱신을 늦춰서, 스크롤하면 이전 이력을 불러오는 잔디 목록이 끝까지 안 읽힐 수 있다. 그래서 `paste.html`의 버튼이 잔디를 몰래 열어 읽는 구조는 믿을 수 없다.
- 토큰(접근 코드)·시트 상태·디자인 부품은 `paste.html`에 있다. 잔디 탭(다른 주소)에 접근 코드를 두면 안 되므로 등록은 반드시 `paste.html`에서 한다.
- `paste.html` 쪽에는 `잔디 ↗` 바로가기와 "설치 방법·마지막 수집 시각"만 둔다.

## 3. 읽기 규칙

### 3-1. 어디까지 읽나 (북마크릿)
- 읽는 사람은 토미·스티브 2명이므로 북마크 코드는 코드째 담아 두고 바뀌면 2대에서 교체한다.
- 방 확인: 주소가 잔디 도메인이고 방 제목이 `U사장님-콘텐츠상품`이 아니면 읽지 않고 "방을 열고 눌러 주세요"만 알린다.
- 범위 기본값 = 마지막 성공 수집 시각 3일 전부터(겹치게 읽어 한 번 놓쳐도 다음에 잡는다). 처음이거나 기록이 없으면 방 처음까지.
  - 선택지: `범위 · 지난 수집부터`(기본) / `최근 14일` / `방 처음까지`.
- 스크롤: 위로 올리며 이전 이력을 불러온다. 한 번에 화면 높이의 60%씩만 올려서 직전 화면과 반드시 겹치게 한다. 겹치는 글이 하나도 없으면 건너뛴 구간이 있다는 뜻이라 되감아 절반 폭으로 다시 올린다.
- 가상 스크롤 처리: 화면에 있는 글만 DOM에 있으므로 스크롤 한 단계마다 보이는 `.msg-layout-flex`를 먼저 모아 두고 나서 올린다. 메시지 고유 ID가 있으면 그것으로, 없으면 `날짜+시각+보낸이+본문 앞 40자` 해시로 중복을 제거한다(ID 속성은 미확인, 슬라이스 1에서 확인).
- 멈추는 조건:
  1. 범위 시작 시각보다 오래된 글이 화면에 보인 뒤 한 화면 더 읽었다(정상 종료).
  2. 3번 연속 새 글이 안 늘어난다(방 처음 도달, 정상 종료).
  3. 80단계 또는 90초 초과(비정상 종료). 이때는 `끝까지 못 읽음`으로 표시하고 수집 시각을 갱신하지 않는다.
- 읽는 중 새로 올라온 글을 놓치지 않게 마지막에 맨 아래를 한 번 더 모은다.
- 전송 최소화: 후보(아래 느슨한 신호가 하나라도 있는 글)의 원문만 보낸다. 잡담 본문은 보내지 않고 `읽은 글 총 N개`, `이미지만 있는 글 N개`(세기만 하고 읽지 않음), `가장 오래된 글 시각`, `끝 도달 여부`만 보낸다.
- 구조 변경 감지: 메시지 컨테이너가 0개로 읽히면 "잔디 화면 구조가 바뀐 것 같아요. 개발팀에 알려 주세요"를 띄우고 아무것도 전송하지 않는다.

### 3-2. 1차 엄격 규칙 (GAS, 자동 등록 대상)
- 글 하나(메시지 단위)를 따로 판정한다. 여러 글을 이어 붙인 덩어리에서 찾지 않는다.
- 통과 조건 전부: 글이 `[Web발신]`으로 시작, `[상품 결제완료]` 줄, 다음 줄 `지점명(숫자)`, `결제상품:`, `결제금액:`, `결제일시: yy.mm.dd HH:mm`이 있고 날짜가 실제 달력에 존재.
- 현재 `parsePaymentAlert_` 규칙을 그대로 이어받고(공백 차이만 허용), "글 처음이 `[Web발신]`" 조건만 더한다. 이 조건이 인용 글을 거른다.

### 3-3. 2차 느슨한 규칙 (자동 등록 안 함, 확인 필요로만)
- 목적: 오타·형식 변형·사람이 고쳐 올린 글을 놓치지 않고 사람 눈 앞으로 올리기.
- 정리: 공백 전부 제거, 전각을 반각으로, 영문 소문자로 맞춘 뒤 신호를 센다.
  - 신호: `결[제재]완료`, `결[제재]상품`, `결[제재]금액`, `결[제재]일시`, `Web발신`, 줄 끝 `(숫자 3~8자리)`, `yy.mm.dd` 꼴 날짜, `블로[그거]` 또는 `빌리투어`.
  - 후보 = 신호 3개 이상, 또는 `결[제재]완료`와 다른 신호 하나.
- 후보가 1차 엄격 통과를 못 하면 느슨하게 지점·번호·날짜·상품을 다시 뽑아 본다.
  - 네 가지가 다 뽑히면: 읽은 결과와 원문을 같이 보여 주고 사람이 `이 내용으로 등록`을 건별로 누른다(일괄 등록 없음).
  - 하나라도 못 뽑으면: 원문과 못 읽은 항목을 보여 주고 `원문 복사`만 준다.
- 등록한 사람이 누구인지는 기록하지 않는다(접근 코드가 공용). 필요하면 별도 결정.

### 3-4. 확인 필요 목록 (조용히 버리지 않는 흐름)
- 1차 실패 + 2차 후보인 글, 지점·날짜 중 하나가 안 읽힌 글, 상품 문구가 블로그·빌리투어 어느 쪽도 아닌데 오타로 보이는 글은 전부 `확인 필요`다.
- 확인 필요는 `잔디 수집 로그` 시트 탭(4-4)에 상태 `확인필요`로 남아 다음 가져오기 때도 다시 뜬다. 사람이 `처리함`을 눌러야 빠진다. 팝업 문구로 흘려보내지 않는다.
- 각 줄: 잔디 시각 / 사유 한 줄(`지점 번호를 못 읽었어요`, `결제일시 형식이 달라요` 등) / 원문 펼치기.

### 3-5. 빌리투어 쉼표 분리
- `결제상품:` 줄을 괄호 밖 쉼표로만 나눈다(`블로그 일반형, 빌리투어 (투어영상)`는 2개, 괄호 안 쉼표 `빌리투어 (영상, 사진)`는 1개).
- 조각마다 분류: `블로그\s*(일반형|고급형)` = 블로그 흐름, `빌리투어` = 빌리투어 흐름(괄호 안 글자는 옵션으로 보관), 둘 다 아니면 `대상 아님`.
- 한 글에서 조각이 둘이면 각각 따로 판정·등록한다. 메시지 전체 `결제금액`은 쪼개지 않고 빌리투어 행에 원본 값으로만 남긴다.
- 금액 점검: 조각 단가 합(일반 70,000 · 고급 150,000 · 빌리투어 400,000)과 결제금액이 다르면 줄에 경고만 붙이고 등록은 진행한다(쿠폰·할인 유무 미확인, 막으면 정상 건이 걸릴 수 있다).

### 3-6. 대상 아닌 건과 인용 글
- 대상 아님 = 엄격 통과인데 상품이 블로그·빌리투어가 아닌 글. 숨기지 않고 `대상 아님 N건`으로 센다(상품 문구를 한 줄로 보여 준다).
- 양식 안내 글(운영이 결제 양식을 따옴표처럼 인용한 글): `[상품 결제완료]`가 있어도 글이 `[Web발신]`으로 시작하지 않거나, 지점 자리에 `지점명`·`OOO` 같은 자리표시 글자, 날짜 자리에 `yy.mm.dd`가 있으면 `안내 글`로 분류하고 확인 필요에 넣지 않는다. 단 건수는 센다.
- 위 두 규칙은 11.24 실측의 잡담 15건·안내 글에 대고 검증해야 확정된다(원문 미열람). 슬라이스 2의 시험 자료로 쓴다.
- 잔디 방의 잡담은 그대로 둔다. `[상품 결제완료]`도 `결[제재]완료` 같은 결제 문구 신호도 없는 글은 후보가 되지 않아 잡히지 않는다. 느슨 규칙의 문턱을 "신호 3개 이상(또는 결제완료 + 다른 신호 하나)"으로 둔 것은 잡담이 확인 필요를 도배하지 않게 하려는 것이다.
- **권고(운영 규칙 한 줄): 결제 알림은 원문 그대로 전달해 올린다.** 사람이 문구·줄바꿈·숫자를 고쳐 올린 글은 엄격 규칙을 통과하지 못해 확인 필요로 밀리고, 느슨 규칙으로도 일부 항목을 못 읽을 수 있다. 말을 덧붙일 때는 원문을 고치지 말고 별도 글로 올린다. 이 문장은 `paste.html` 사용 방법과 북마크 설치 안내에 한 줄로 넣는다.
- 이미지 글(토스 알림톡 캡처)은 이번 범위에서 제외로 확정이다. 읽지 않고 후보로도 세지 않는다. 읽지 않은 이미지가 몇 건인지만 센다(5절 참고 줄).

## 4. 등록 흐름과 중복 방지

### 4-1. GAS 새 동작
기존 `doPost` 분기에 두 개를 얹는다. 기존 `registerPayment`(붙여넣기)는 그대로 둔다.
1. `previewJandi {token, messages[], scan{}}`: 읽기 전용. 분류만 돌려준다. 시트·속성에 아무것도 쓰지 않는다.
2. `importJandi {token, messages[], confirm[]}`: 서버가 원문을 다시 분류하고(클라이언트 분류를 믿지 않는다) `confirm`에 든 건만 쓴다. `LockService` 스크립트 잠금 아래에서 실행하고, 같은 호출을 두 번 보내도 결과가 같다(멱등).
- 분류 값: `이미있음` / `새로등록`(일반형) / `번호필요`(고급형) / `빌리투어쌓기` / `대상아님` / `안내글` / `확인필요`.
- 고급형 전화번호 입력과 알림톡 발송은 지금의 `registerPremium` 흐름을 그대로 쓴다.
- 일반형 등록 본문은 `registerOnePayment_`를 함수로 쪼개 같이 쓴다. 현재 중복 확인이 최근 200행·직-일반만 보는 점은 이번에 2,000행(`listStatus`와 같은 상한)으로 맞춘다.
- 코드를 고치면 `Code.gs`의 `BUILD`와 `GAS 배포 (딸깍).bat`의 `findstr` 값을 같이 바꾼다(기존 규칙). GAS 변경·재배포는 토미 전담.

### 4-2. 중복 키 (지점번호 + 결제일시, 분 단위)
| 종류 | 이미 있음 판정 |
|---|---|
| 일반형 | `직-일반` 행에서 신청자 칸 끝 `(번호)`가 같고 결제완료일(B) 분 단위가 같음. 지점명이 바뀌어도 번호로 맞춘다 |
| 고급형 | 아래 셋 중 하나: ① 알림톡 발송 기록(`PF_번호_결제일시`) ② `직-대기` 행의 같은 번호 + 같은 결제일시 ③ `직A`·`직B` 행의 같은 지점번호(E열 주소) + 결제완료일(B)이 같음(11.23 이후 행은 결제일시를 유지) 또는 결제일시 이후 14일 안(11.23 이전 행은 B가 폼 제출일) |
| 빌리투어 | `부가상품 결제` 탭에서 지점번호(C열) + 결제일시(A열)가 같음 |
- 고급형 ③은 한 행이 한 결제와 한 번만 짝이 되게 시간순으로 1:1 대응시킨다(같은 지점이 두 번 결제해도 한 행으로 둘이 덮이지 않게).
- 14일은 가정이다(폼 제출이 결제 뒤 최대 며칠인지는 미확인). 날짜 차이가 애매하면 `번호필요`로 올리고 카드에 "같은 지점 직A 행 있음(차이 N일)"을 함께 보여 사람이 정한다. 틀린 "미등록"은 사람이 거를 수 있지만 틀린 "이미 있음"은 놓침이므로, 애매하면 항상 드러내는 쪽으로 쓴다.

### 4-3. 20897 같은 미등록 고급형을 드러내는 방법
- 고급형은 사장님 전화번호가 있어야 알림톡이 나가서 자동 등록이 불가능하다. 그래서 대조 결과에 별도 줄 `전화번호가 필요한 고급형 N건`으로 올리고, 줄을 누르면 지금의 전화번호 카드가 열린다.
- 20897은 시트에 번호가 전혀 없고 발송 기록도 없으니 ①②③ 어디에도 안 걸려 이 줄에 뜬다. 카드 사유 한 줄 = `시트·발송 기록에 이 지점이 없어요`.
- 이미 오래전에 처리돼 더는 필요 없는 건(예: 사장님이 다른 경로로 해결)은 카드의 `해당 없음`으로 닫으면 로그에 `종결`로 남아 다시 뜨지 않는다.

### 4-4. 빌리투어 쌓을 곳: 신청 내역에 섞지 않고 같은 파일의 새 탭으로

**검토 결론: 맞다. 신청 내역 시트에는 빌리투어 행을 섞지 않고, 같은 스프레드시트 파일(`SPREADSHEET_ID`) 안에 새 시트 탭을 두고, `paste.html`이 두 시트를 합쳐 읽는 안이 가장 안전하다.** 블로그 시트를 "부가상품 시트"로 열 구조째 확장하는 안(신청 내역에 열을 더하거나 행을 섞기)은 아래 근거로 채택하지 않는다.

이번에 저장소 코드에서 읽어 확인한 것(11.24):
| 읽는 쪽 | 시트를 찾는 방식 | 새 탭을 만들면 | 신청 내역에 빌리투어 행을 섞으면 |
|---|---|---|---|
| 기존 GAS 3개(10만원·15만원·직접결제) | 탭 이름(`신청 내역`·`완료 내역`·`설정`)으로 열고 열 번호로 읽음. 편집 트리거 `onSheetEdit`도 `sheetName === '신청 내역'` 조건 | 영향 없음. 새 탭에서 사람이 고쳐도 트리거가 무시함 | M열(작성 타입)·N열(상태)·P열(단가) 규칙에 빌리투어 값이 끼어 색칠·D-day·리마인드가 오동작할 수 있음 |

- 중복 위험(미확인, 토미 확인 필요): 어드민에는 이미 빌리투어숏폼 신청 시트(별도 파일, 다른 id)가 매출 소스로 걸려 있고 CS앱에도 `빌리숏폼` 인박스가 있다. 이번에 잔디에서 읽는 `빌리투어 (투어영상)` 결제가 그 신청 시트에도 따로 입력되는 상품인지 모른다. 같은 상품이면 두 곳에 기록이 남을 수 있다. 새 탭은 어드민 매출 집계에 잡히지 않으므로 매출 이중 계상은 없고, 사람이 두 시트를 봐야 하는 혼선만 남는다.

새 탭 2개 (둘 다 추가만 한다):
- 탭 1 `부가상품 결제`: 지금은 빌리투어만 쌓는다. 블로그 일반형·고급형은 계속 `신청 내역`에만 있고 이 탭에 복제하지 않는다(같은 사실을 두 곳에 두지 않는다). 공통 열만 둔다.
  | 열 | 내용 |
  |---|---|
  | A | 결제일시 (`yyyy-MM-dd HH:mm`) |
  | B | 지점명 |
  | C | 지점번호 |
  | D | 상품 (`빌리투어 (투어영상)`처럼 괄호 안 옵션까지 원문 그대로) |
  | E | 금액 (그 상품 조각의 단가, 등록 시점 값 그대로. 400,000, 부가세 포함) |
  | F | 상태 (`진행전`) |
  - 중복 키 = 지점번호 + 결제일시(분). 탭 이름이 `빌리투어 결제`가 아니라 `부가상품 결제`인 것은 상품 열로 다음 상품을 같은 형식에 받기 위해서다. 상품이 빌리투어 하나뿐인 동안은 이름만 다를 뿐 추가 비용이 없다.
  - 한 글에 블로그와 빌리투어가 같이 있어도 이 탭에는 빌리투어 조각만 한 행으로 들어간다. 같은 글의 블로그 동반 여부, 메시지 전체 결제금액, 원문은 이 탭에 넣지 않고 로그 탭에 둔다(공통 열만 유지).
- 탭 2 `잔디 수집 로그`: 수집일시 / 키(번호+결제일시) / 지점 / 판정 / 사유 / 원문(1,000자까지) / 같은 글의 동반 상품 / 메시지 결제금액 / 종결일시. 같은 키+같은 판정은 다시 쓰지 않는다. 확인 필요·번호 필요의 "상태 저장소"이자 읽기 회귀 점검(6절)의 기준이다.

`paste.html`이 두 시트를 합쳐 읽는 방법:
- GAS `listStatus`가 지금처럼 `신청 내역` 기반 `items`를 그대로 돌려주고, 같은 응답에 `부가상품 결제` 탭을 읽은 `billy` 배열을 따로 더한다. 기존 `items`의 모양을 바꾸지 않으므로 지금 화면이 깨지지 않는다.
- 화면은 이미 있는 `블로그 | 빌리투어` 상품 탭(`.ptabs`)에서 빌리투어 칸의 "연결 전" 안내를 읽기 전용 표로 교체한다. 블로그 탭의 시트 DB 표에는 빌리투어를 섞지 않는다(상품마다 등록·현황이 한 벌이라는 디자인 시스템 규칙).
- 결제 추이 카드의 `구분` 드롭다운은 디자인 게이트에서 정한다. 11절의 요구대로 `구분`을 `블로그(고방 매출, 기본)` / `빌리투어` / `전체`로 나누고 빌리투어 데이터가 들어오는 때(슬라이스 6)에 함께 바꾼다. 기본값이 블로그라 빌리투어 400,000원이 들어와도 블로그 추이는 흔들리지 않는다.
- 빌리투어 유형 아이콘 1개가 새로 필요하다(이름만: `빌리투어` 아이콘, 실루엣이 문서·왕관·클립보드와 달라야 함).
- 빌리투어의 이후 처리 흐름(작업 배정·완료·알림)은 이번 범위가 아니다. 이번에는 "쌓기 + 읽기 전용 표"까지만 한다.

## 5. 누락 대조 화면

버튼을 누를 때마다(가져오기 결과든 붙여넣기든) 대조 카드를 한 장 보여 준다. 결과는 건수가 먼저, 사유는 한 줄씩이다.

요청한 4개(읽은 / 이미 있음 / 새로 등록 / 확인 필요)에 두 줄을 더한다. 고급형 미등록은 오류가 아니라 사람이 할 일이라 "확인 필요"와 섞지 않고, 대상 아님은 숨기지 않고 센다. 합계가 맞아야 "하나도 안 놓침"을 눈으로 확인할 수 있다.

문구 방향(해요체, 화면 글은 최소):
```
잔디에서 결제 알림 21건 읽었어요            <- res-title
10.29 ~ 11.24 · 방 처음까지 읽음            <- res-sum (끝까지 못 읽었으면 "11.12 까지만 읽었어요")
 이미 시트에 있음           13건
 새로 등록할 일반형          0건
 전화번호가 필요한 고급형    1건   20897 · 11.06 10:01 · 시트에 이 지점이 없어요
 빌리투어 쌓을 것            8건
 확인 필요                   0건
 대상 아님                   1건
 안내 글                     (건수만)
 읽지 않은 이미지 25건      (범위 밖, 회색 참고 줄. 합계 점검에는 넣지 않음)
```
- 이미지 캡처는 범위 밖이라 등록·판정 대상이 아니고 합계 점검에도 넣지 않는다. 읽지 않은 건수만 참고 줄로 보여 주고, 카드 머리 ⓘ 툴팁에 "텍스트 결제 알림 기준이에요. 이미지 캡처는 읽지 않아요" 한 줄을 둬서 "하나도 안 놓침"의 범위가 텍스트 알림에 한정된다는 것을 화면이 밝힌다.
- 합계 점검 한 줄: `읽은 21건 = 13 + 0 + 1 + 8 + 0 + 1 - 같은 글 안의 중복 조각 N`. 안 맞으면 화면이 "건수가 안 맞아요"를 띄우고 등록 버튼을 잠근다.
- 등록 버튼 `시트에 등록하기`는 기존처럼 확인 팝업을 거친다(되돌릴 수 없는 시트 쓰기). 팝업은 "일반형 N건, 빌리투어 N건을 등록합니다. 확인 필요 N건은 등록하지 않아요" 정도만 말한다.
- 읽은 방 범위가 `끝까지 못 읽음`이면 카드 맨 위에 경고 한 줄을 두고 수집 시각을 갱신하지 않는다.

기존 어휘로 만든다(`docs/design-system.md`):
| 필요한 것 | 쓰는 부품 |
|---|---|
| 카드 바탕·제목·한 줄 요약·확인 | 결과 카드 `#out`의 `.res-title` `.res-sum` `.res` `.res-ok` |
| 줄마다 상태 | 상태 칩 `.chip` (회색 = 이미 있음·대상 아님, 노랑·주황 = 사람이 할 일, 초록 = 끝) |

| 설명 문장 | 툴팁 `.tip` |
| 등록 확인 | 확인 팝업 `.modal`/`.sheet` |
| 고급형 번호 입력 | 지금의 `askCard` |
| 잔디 바로가기 | `.quick` (결제 알림 카드 머리, U사장님 ↗ 옆) |
| 빌리투어 표 | 상품 탭 `.ptabs`의 빌리투어 칸(지금 "연결 전" 안내 카드를 읽기 전용 표로 교체) + `.tr` `.c-kind` |

- 새 화면 파일 제안: 순수 함수 `js/jandi-recon.js`(응답을 화면 데이터로 바꿈, `node tests/`로 시험), 수신 `js/jandi-bridge.js`. `paste.html`은 1,344줄 단일 파일이라 더 키우지 않는다(`js/trend-calc.js`와 같은 방식).
- 프로젝트 파이프라인상 UI 변경이므로 화면 구현 전 디자인 게이트(옵션 2~3개 제시·컨펌)를 거친다. 이 절은 방향까지다.

## 6. 위험과 한계

1. **잔디 화면 구조가 바뀌면 깨진다.** 잔디가 약속한 인터페이스가 아니라 화면 글자를 읽는 방식이다. 대응: 컨테이너 0개 감지 시 중단 경고, 읽기 회귀 점검(아래 2번), 셀렉터 한 곳에 모으기.
2. **읽기 회귀 점검(놓침 방지 2중 장치).** 지난 수집 로그에 있던 결제(이번 범위 안)가 이번에 안 보이면 "지난번엔 있었는데 N건이 안 보여요"를 띄운다. 스크롤이 덜 읽혔다는 신호이고, 사람이 눈치채지 못하는 읽기 누락을 잡는 유일한 자동 장치다.
3. **브라우저가 꺼져 있던 시간.** 가져오기는 사람이 누를 때만 일어난다(자동 수집 없음). 안 눌러도 잔디 이력은 남아 있으므로 건이 사라지진 않고 늦어질 뿐이다. 범위 기본값이 마지막 성공 수집 3일 전이라 며칠 쉬어도 이어서 읽는다. `paste.html` 머리에 `마지막 수집 11.24 10:12`를 보여 오래 안 눌렀음을 알린다. 누가 얼마나 자주 누를지는 운영 규칙이라 별도 결정이다.
4. **잔디 약관: 미확인.** 본인 계정·본인 브라우저에서 화면을 읽는 방식이고 토큰 추출·계정 공유가 없어 C보다 위험이 낮지만 자동 화면 읽기 조항은 확인하지 못했다. 시험 전에 약관 확인이 필요하다.
5. **접근 코드 보관.** 지금처럼 `paste.html`의 브라우저 저장소에만 둔다. 북마크릿은 코드를 보지도 받지도 않는다. 전달 창구는 받는 쪽에서 보낸 주소(잔디 도메인)만 허용하고 글자는 `textContent`로만 그린다(잔디 글을 `innerHTML`로 넣으면 스크립트 주입 통로가 된다). GAS는 받은 원문을 신뢰하지 않고 서버에서 다시 분류한다.
6. **이미지 건 제외(확정).** NF운영이 올린 토스페이먼츠 알림톡 캡처 25건(글자 없음)은 이번 범위가 아니다. 이 이미지가 텍스트 21건과 겹치는지, 별개 결제인지는 확인하지 않았다(미확인). 그래서 보장 범위는 "텍스트 결제 알림"까지이고, 화면 툴팁이 이를 밝힌다.
   - 나중에 붙일 방법(참고, 이번 범위 아님) 1순위: NF운영이 캡처 대신(또는 같이) "[상품 결제완료]" 텍스트를 올리게 하는 요청. 코드를 짜지 않고 프로세스로 푸는 방식이라 가장 싸다(개발 원칙 2번).
   - 2순위: 토스페이먼츠 웹훅. 토스페이먼츠에 웹훅 기능이 있다는 것은 알려져 있으나, 이 상점 계정의 권한자가 누구고 쓸 수 있는지는 미확인이다. 11.09에 잔디 웹훅이 없다고 결정한 것과 별개다. 확인 먼저, 설계는 그 뒤.
   - 비추: 이미지를 AI로 읽기. 오독 위험·비용이 있고 결제 금액이 걸린 데이터라 검증 부담이 커진다.
7. **가격이 바뀌면** 단가 상수(`PRICE_DIRECT_BASIC` 등)와 금액 점검 값을 같이 고친다(README 기존 규칙).
8. **잔디에서 글을 수정·삭제하면** 이미 등록한 행은 따라 바뀌지 않는다. 범위 밖(시트의 행은 사람이 고친다).

## 8. 3.5단계 리소스 승인 표

**승인 전에는 아무것도 만들지 않는다.** 이 문서(스펙)와 승인 요청까지만 한다. 코드·시트 탭·배포는 모두 승인 뒤.

| 항목 | 용도 | 비용 | 필요한 권한·계정 | 비고 |
|---|---|---|---|---|
| npm 패키지 | 없음 | 0 | 없음 | 바닐라 JS, 시험은 기존처럼 `node` |
| 북마크릿(안 B) | 잔디 탭에서 읽기 | 0 | 토미·스티브 각자 크롬과 본인 잔디 로그인 | 설치 = 2대에 북마크바에 끌어다 놓기, 심사 없음 |

| 외부 서비스 | 없음 | 0 | 없음 | GAS·GitHub Pages·시트는 기존 것 |
| GAS 변경 | `previewJandi`·`importJandi` 추가 | 0 | `clasp push` + 같은 배포 ID로 재배포 | 토미 전담. `BUILD`·bat의 `findstr` 같이 갱신 |
| 스크립트 속성 | 마지막 수집 시각 저장 | 0 | 편집기에서 추가 | 값은 시각뿐. 비밀 값 아님 |
| 시트 새 탭 2개(같은 파일, 맨 뒤) | `부가상품 결제`(공통 열 6개), `잔디 수집 로그` | 0 | 시트 편집 권한(기존) | 신청 내역의 열·행은 변경 없음. 어드민은 파일 id + gid 0, GAS 3개는 탭 이름으로 읽음을 코드로 확인. 바인딩 스크립트·수식은 미확인 |

| 배포 | `paste.html`·`js/` | 0 | 기존 GitHub Pages | 변경 없음 |

## 9. 개발팀장 의견

가장 위험한 가정 두 가지:
1. **"잔디에 올라오는 텍스트 결제 알림이 사람이 원문대로 올린다."** 이미지 건은 범위 밖으로 확정했지만, 텍스트 글도 사람이 고쳐 올리면 읽기가 틀어진다(엄격 규칙 탈락 후 확인 필요로 밀린다). 대응: "원문 그대로 올리기" 권고를 사용 방법에 두고, 못 읽은 건은 확인 필요 목록으로 남긴다. 이미지 캡처가 별개 결제일 가능성(25건 대 21건)은 확인하지 않았으므로 화면 툴팁에 보장 범위가 "텍스트 결제 알림"임을 밝힌다.
2. **"잔디 화면 글자는 끝까지 안정적으로 읽힌다."** 11.24에 한 번 본 구조이고 잔디가 약속한 인터페이스가 아니다. 한 번 놓치면 사람은 눈치채지 못한다. 대응: 겹치는 스크롤, 구조 변경 감지, 읽기 회귀 점검 세 장치를 슬라이스 1·7에 필수로 넣는다.

반대 의견 하나: **수집 자동화의 효과는 작고 대조의 효과가 크다.** 결제는 하루 1건이 안 된다(26일간 21건). 붙여 넣는 수고 자체는 작고, 아픈 곳은 14건 중 1건(7%)이 시트에서 빠진 것이다. 그래서 만드는 순서도 "읽기 자동화 먼저"가 아니라 "대조 먼저"(슬라이스 2, 3)가 맞다. 붙여넣기만으로도 대조 카드가 돌면 이번 누락은 잡힌다. 읽기 자동화(북마크릿)는 그 위에 얹는 편의다. 자동화를 먼저 하면 "자동으로 잘 되고 있다"는 착각 속에서 읽기 누락이 조용히 생길 위험이 있다.

확장(A)이 낫다는 의견도 있을 수 있다. 잔디 화면에 버튼이 떠 있어 UX가 좋다는 점은 맞다. 다만 사용자가 2명이라 설치 인프라(스토어 게시, 자동 업데이트)는 필요 없고, 압축해제 확장은 개발자 모드 경고·폴더 보관이라는 관리 부담이 생긴다. 북마크릿으로 써 보고 불편이 확인되면 그때 압축해제 확장으로 옮긴다(읽기 로직은 같은 코드라 이전 비용이 작다).

빌리투어를 신청 내역 시트의 열 구조째 확장하는 안에 대한 반대 의견: 기존 GAS 3개는 열 번호로, 어드민은 헤더 이름으로 신청 내역(gid 0)을 읽어 블로그 매출에 합산하므로 행을 섞으면 어드민 매출 분류까지 틀어진다. 같은 파일의 새 탭은 코드상 영향이 없어서 이 안이 낫다(4-4). 단 저장소 밖 스크립트·수식은 못 봤으니 착수 전 한 번 훑는다.

## 10. 토미가 정해야 할 것

1. 읽기 방식

2. 만드는 순서
   - 2-1. (추천) 대조 먼저(슬라이스 2, 3, 4), 읽기 자동화(슬라이스 1, 5)는 병렬 시험 후 연결. 이번 누락 건이 먼저 잡힌다.
   - 2-2. 읽기 자동화 먼저. 눌러 보는 맛은 빠르지만 대조 없이는 놓침 방지가 아니다.
3. 빌리투어 저장 방식(신청 내역에 섞는 안은 열 구조 변경 불가 조건으로 제외)
   - 3-1. (추천) 같은 스프레드시트 파일의 새 탭 `부가상품 결제`(공통 열 6개)에 쌓고 `paste.html`이 두 시트를 합쳐 읽는다. 어드민·GAS 3개는 코드상 영향 없음. 토미 확인 하나: `빌리투어 (투어영상)` 결제가 기존 빌리숏폼 신청 시트(어드민 매출 소스)에도 따로 입력되는가. 같으면 두 곳에 기록이 남는 혼선이 생기고, 매출 이중 계상은 새 탭이 어드민에 안 잡혀서 없다.
   - 3-2. 별도 스프레드시트 파일. 기존과 완전히 분리되지만 파일이 하나 늘고 GAS가 다른 파일을 열어야 하며, 추이·대조에서 두 파일을 합치는 코드가 더 필요하다.

## 11. 토미 결정·추가 요구 (11.24, clear 전 인수인계)

- 사용 인원은 토미와 스티브님 2명이고 둘 다 크롬과 잔디 계정이 있다. 스티브님이 이 잔디 방 멤버인지는 미확인.
- 이미지(토스 알림톡 캡처 25건)는 이번 범위에서 제외한다. 대조 카드의 "읽지 않은 이미지 N건"은 유지한다. 잔디 방 잡담은 그대로 두고, 결제 알림 "원문 그대로 전달"만 권고한다.
- 결제 알림 메시지 복붙 칸은 버튼으로 뺐다. 잔디에서 긁어오는 것이 기본이고, 안 읽힌 건만 `안 읽힌 건 붙여넣기`로 넣는다. 시트 DB는 전체 폭으로 넓혔다. 블로그/빌리투어 상품 탭은 `paste.html`에 이미 있다. 가져오기 버튼은 잔디 연결 전이라 비활성이다.
- 빌리투어 저장 위치: 블로그 시트 파일 안에 새 탭을 두는 안(토미 의견: 블로그 시트를 부가상품 시트로 확장). 기존 `신청 내역` 탭에는 섞지 않는다. 승인은 아직이다.
- **결제 추이 구분 요구(토미 11.24)**: 고방 매출로 보는 것은 블로그 건까지이므로 추이에서 상품별로 갈라 볼 수 있어야 한다. 빌리투어 데이터가 들어오는 때에 `구분` 드롭다운을 `블로그(고방 매출, 기본)` / `빌리투어` / `전체`로 나누고, 블로그는 부가상품 블로그 + 기존 폼의 합으로 센다. 지금은 빌리투어 데이터가 없어 추이가 이미 블로그만이다.
- 디자인팀장 등록 요청: `design-system.md`에는 `.ptabs`·`.hidechk`·`.tr.wr` 행이 11.24에 디자인팀장을 거치지 않고 올라가 있다(검수 필요). `.tgl`(테두리 토글 버튼, `.ptab`과 같은 모양), `.regbar`(결제 알림 줄: 가져오기 채움 버튼 + 붙여넣기 접기), `.cols` 한 칸 전체 폭(옛 380/1fr 두 칸 행 57 갱신)은 미등록이다.
- 남은 확인: 20897(휴식 교대점, 11.06 고급형) 처리 여부(토미), 스티브님 잔디 방 멤버 여부. 어드민·CS앱이 시트 전체 탭을 훑는지는 코드로 확인했다(4-4: 어드민 = 파일 id + gid 0, CS앱 = 블로그용 GAS 경유, GAS 3개 = 탭 이름). 저장소 밖 바인딩 스크립트·수식만 미확인. `paste.html` 변경은 푸시 전이고 화면은 눈으로 확인하지 못했다.

### 11-1. 빌리투어 DB를 숏폼 원장으로 쓰자는 토미 제안 (11.24, 확인 결과와 위험, 미결정)

- 토미 답: 빌리투어 결제는 기존 어디에도 따로 입력되지 않는다. 숏폼 원장에 넣고 블로그 DB와 빌리투어 DB를 둘로 가르자. 이 제안이 4-4의 "신청 내역 탭 안 섞고 새 탭 `부가상품 결제`" 안을 대체할 후보다.
- 숏폼 원장 실물(11.24 읽기 확인): `[NF]_빌리투어 숏폼판매_R`(id `1kF48mlpvfI-2R1spXXNLECLg-wUd_u_YzcHHO-ztBb0`, gid 1252517232). 열 = 상품·신청자명·연락처·지점명·지점주소·빌리투어 영상 URL·고방 플레이스 URL·메모·결제완료일·결제발송·결제발송시간·결과물URL·완료파일URL·완료발송·완료발송시간·단가. 데이터 9행(전부 숏폼 단건 55,000원, 마지막 결제 11.09). 영상 납품 추적 열이 있어 투어영상 DB로 맞다. `신청일시` 열은 없다.
- 이 시트는 어드민 매출 원장에 매주 일요일 00시 자동 합산된다(`gobang-admin/gas/Code.gs` `SYNC_SOURCES` 269~289줄, 항목 `billyshort`, 최근 8주, 결제완료일 + 단가가 있으면 매출). 행을 넣으면 매출에 바로 반영된다.
- 위험 3개:
  1. 중복 키: 키 = 결과물URL, 비면 `신청일시 + 고방 플레이스 URL`인데 이 시트에 `신청일시`가 없어 place URL 하나뿐이다. 같은 지점이 두 번 사면 한 건으로 덮어써지고, 나중에 결과물URL을 채우면 키가 바뀌어 같은 결제가 두 번 계상된다. 어드민 GAS 키를 `place URL + 결제완료일`로 고쳐야 한다(gobang-admin 변경, 개발팀장).
  2. 매출 항목: 이 시트는 어드민에서 `빌리투어숏폼`(월 목표 15~110만) 한 항목이다. 40만원 투어영상이 숏폼 단건(5.5만)과 한 항목에 섞인다. 투어영상을 별도 항목으로 둘지 토미·기획팀장이 정해야 한다.
  3. 단가: 잔디 결제금액은 먼슬리플랜 합계라 총액을 넣으면 과대 계상이다. 단가표로 투어영상 몫만 넣어야 하고(11.09 결제화면 기준 40만원, VAT 포함, 기존 55,000도 VAT 포함이라 일관), 잔디 메시지에 일반형/고급형 구분이 없어 규칙이 필요하다.
- 미확인: 우리 GAS(addon-direct-pay)의 실행 계정이 이 시트를 열고 쓸 수 있는지, 잔디의 빌리투어 8건(11.03~11.23)이 매출 원장에 다른 경로로 들어가 있는지(숏폼 원장에는 없음).
- 승인 표(8절) 추가 후보: 어드민 `gas/Code.gs` `SYNC_SOURCES` 키 수정과 재배포.

### 11-2. 11-1 번복: 빌리투어는 숏폼 원장에 넣지 않는다 (토미 구두 11.24, 확정)

- 숏폼 원장(`[NF]_빌리투어 숏폼판매_R`)은 옛날 빌리투어 상품 개선과 숏폼을 함께 팔던 곳이라 성격이 겹친다. 지금 숏폼은 55,000원, 빌리투어(투어영상)는 400,000원이다.
- 이 시트에는 숏폼 신청폼으로 접수된 건만 쌓인다. 빌리투어 요청은 신청폼이 없으므로 별도 DB로 따로 쌓는다. 11-1의 숏폼 원장 안은 폐기한다.
- 빌리투어 요청은 연우님께 전달하거나 직접 처리한다. 단계값(작업 상태)은 처음엔 두지 않는다. 나중에 개선하더라도 사람이 직접 누르는 방식이다.
- 11-1의 위험 3개 중 키 중복·항목 섞임·단가는 별도 DB로 가면 대부분 풀린다. 새 DB 키는 지점번호+결제일시, 매출 항목은 빌리투어로 분리하고 단가는 투어영상 40만원 고정으로 정한다(먼슬리플랜 합계를 넣지 않는다).
- 남은 일: 별도 DB 위치(블로그 시트 새 탭 `부가상품 결제` vs 별도 시트), 어드민 `SYNC_SOURCES`에 새 소스 추가(8절 승인 항목), 투어영상 단가 VAT 기준 확인.

### 11-4. 20897 정정 (토미 11.24 스티브님 개인 잔디방 확인, 확정)

- 20897은 누락이 아니다. 스티브님이 알림톡(제출폼)을 이미 발송했고 사장님 회신을 기다리는 중이다. 시트 DB 화면(paste.html)에 11.06 10:01 "지점번호 20897" 고급형 150,000원 "응답 대기"로 떠 있다(스티브님이 보낸 화면 캡처, 11.24 14:21). 지점명이 비어 있는 것은 발송 기록(PF_)에 시각만 남은 옛 건이기 때문이다.
- 따라서 시트에 직접 행을 넣지 않는다. 11-3의 "작성 완료로 직접 기록" 방침은 폐기한다. 블로그는 사장님이 폼을 낸 뒤에 작성한다.
- 분류기 기대값 정정: 실제 20897은 시트에는 없지만 알림톡 발송 기록(PF)에 있어 "이미 있음(응답 대기)"이다. "번호 필요"가 아니다. 실제 21건 대조 결과 기대는 "이미 있음 14, 빌리투어 8, 대상 아님 1"이다.
- 설계 9절의 "14건 중 1건(7%) 누락" 근거는 약해졌다. 이번 건은 발송 기록으로 추적되고 있었다. 대조 먼저 순서의 근거는 "사람이 눈치채지 못하는 읽기 누락 방지"로 남는다.
- 확인 못 한 것: 사장님이 폼을 제출할 때 직-대기 행이 없는 옛 건이 시트에 어떻게 기록되는지(결제완료일이 11.06 원문 시각으로 남는지).

### 11-6. 구현 현황과 배포·확인 목록 (11.24, 개발팀장)

슬라이스 1~7을 코드와 node 시험까지 구현했다. 배포한 것은 없다. 운영 설명의 정본은 `addon-direct-pay/README.md`의 "잔디 가져오기" 절이다.

**1. GAS 새 동작 (`gas-code/Code.gs`, 분류기 `gas-code/JandiClassify.gs`)**
- `previewJandi {token, messages[], scan}`: 읽기 전용 분류. 응답 `{success, readOnly, results, counts, regression:{missing:[{key,branch,paidAt}]}}`. 종결된 확인 필요·번호 필요 조각은 class를 유지하고 `closed:true`와 reason `종결됨`을 붙인다.
- `importJandi {token, messages[], confirm:[{key, action}], scan}`: action = `basic`·`billy`·`close`. 서버가 원문을 다시 분류하고 `confirm`의 key만 쓴다. 스크립트 잠금 안에서 실행하고 멱등이다. 응답 `{success, results:[{key,action,status,reason}], counts:{added,duplicate,closed,skipped,error}, logged, lastScan}`. 한 호출 messages 최대 500건. 고급형은 자동 등록하지 않는다.
- `listStatus`: 기존 `items`·`truncated`·`build`는 그대로, `billy` 배열과 `lastScan`을 더했다.
- 읽기 회귀 점검: 로그 탭의 키 중 이번 messages의 가장 오래된 결제일시 이후인데 이번 글 목록에 없는 것을 `regression.missing`으로 돌려준다.
- 새 탭 2개(같은 스프레드시트, 처음 쓸 때 맨 뒤에 자동 생성): `부가상품 결제`(6열, 금액 400,000), `잔디 수집 로그`(9열). 스크립트 속성 `JANDI_LAST_SCAN`은 끝까지 읽은 스캔만 갱신한다.
- 분류기 보강: 지점번호·결제일시를 못 읽은 확인 필요 글에는 글 해시로 만든 열쇠 `X_xxxxxxxx`를 붙인다(로그·종결용). 느슨 규칙에 "지점명(숫자) + 블로그·빌리투어 + 결제 표현" 신호를 더했다(11.24 실측의 사람이 쓴 안내 글 20803이 잡담으로 버려지던 문제).
- `BUILD` = `2026-11-24-jandi-import`. `GAS 배포 (딸깍).bat`의 `findstr`도 같은 값이다.
- 배포 순서(토미 전담): ① `gas-code`에서 `clasp push` ② 같은 배포 ID로 재배포 ③ `GAS 배포 (딸깍).bat`으로 `build` 값 확인 ④ `paste.html`·`js/`·`js/jandi-bookmarklet.txt`를 GitHub Pages에 올림.

**2. 북마크 설치·갱신**
- 만들기: `addon-direct-pay` 폴더에서 `node scripts\build-bookmarklet.js` → `js/jandi-bookmarklet.txt`(`javascript:` 한 줄, 약 11KB). `js/jandi-reader.js`·`js/jandi-bookmarklet-src.js`·`js/jandi-bridge.js`(`EXPECTED_VERSION`)의 `READER_VERSION`이 다르면 빌드가 실패한다.
- 설치: 토미·스티브가 각자 `paste.html`의 `설치 방법`에서 `NF 결제 가져오기`를 북마크바로 끌어다 놓는다.
- 갱신: 읽기 코드가 바뀌면 `READER_VERSION`을 세 곳 모두 올리고 빌드하고 올린 뒤 2대에서 북마크를 다시 끌어다 놓는다. 옛 북마크는 화면이 "북마크가 오래됐어요"로 알린다(북마크 버전 표식). 올릴 때 README의 버전 줄과 `paste.html` 설치 칸의 `북마크 버전 N` 문구를 같이 고친다. 배포 bat의 값은 GAS `BUILD` 전용이라 `READER_VERSION`과 따로 관리한다.
- 현재 `READER_VERSION` = 1.

**3. 화면 연결 흐름**
잔디 탭에서 북마크 클릭 → 방을 끝까지 읽음(패널에 진행 표시, 탭을 그대로 둠) → `결과 화면으로 보내기` → `paste.html` 새 창이 postMessage로 받음(보낸 곳이 잔디 도메인일 때만, 북마크는 `paste.html` 배포 출처로만 보냄) → GAS `previewJandi` → 대조 카드(건수가 먼저, 사유는 한 줄씩, 합계가 안 맞으면 등록 잠금) → `시트에 등록하기`(확인 팝업) → GAS `importJandi` → 현황·빌리투어 표·`마지막 수집` 갱신. 끝까지 못 읽었으면 카드 맨 위에 경고를 띄우고 수집 시각을 갱신하지 않는다.

**4. 미배포·미확인 (결제 금액이 걸린 데이터라 하나도 단정하지 않는다)**
1. 실제 GAS에서 한 번도 돌리지 않았다. 시트·속성 목 시험만 했다. `insertSheet`로 만든 탭 위치, 잠금, 날짜·`₩` 서식은 배포 뒤 확인한다.
2. 실제 잔디 화면에서 북마크를 실행해 `window.open`으로 `paste.html`을 열고 postMessage로 넘기는 연결은 돌려 보지 않았다. 브라우저의 창 간 격리 정책(COOP)이 이 연결을 막는지도 미확인이다. 읽기만 11.24에 실제 방에서 시험했다(11-5).
3. 약 11KB `javascript:` 북마크가 크롬 북마크 동기화와 북마크바에서 그대로 유지되는지 미확인이다.
4. 잔디 방 주소(`js/jandi-ui.js`의 `JANDI_ROOM_URL`)는 11.24 실측한 주소를 가정한 값이다.
5. 잔디 약관(자동 화면 읽기 조항) 미확인.
6. 저장소 밖 시트 바인딩 스크립트·시트 안 수식이 새 탭 2개를 건드리는지 미확인(4-4).
7. 붙여넣기 등록(`registerPayment`)은 대조 카드를 거치지 않는다. 안 읽힌 건을 붙여 넣을 때는 시트와의 대조가 없다.
8. `paste.html` 접근 보호는 접근 코드 한 가지다. 코드를 아는 사람은 누구든 등록할 수 있고 등록한 사람은 기록되지 않는다(3-3).
9. 14일 창(고급형 폼 제출이 결제 뒤 며칠 안인지)은 가정이고, 사장님이 폼을 낼 때 직-대기 행이 없는 옛 건의 시트 기록(11-4)도 미확인이다.
10. 화면 쪽 파일(`js/jandi-recon.js`·`js/jandi-ui.js`·`js/jandi-bridge.js`)은 다른 에이전트가 만들었다. 이 문서는 그 파일과 시험이 있다는 것까지만 확인했고 화면은 눈으로 보지 않았다.

**5. 운영 규칙**
- 결제 알림은 원문 그대로 올린다(3-6의 권고). 사람이 문구·줄바꿈·숫자를 고쳐 올린 글은 엄격 규칙을 통과하지 못해 확인 필요로 밀리고 일부 항목은 못 읽을 수 있다. 말을 덧붙일 때는 원문을 고치지 말고 별도 글로 올린다. 이 한 줄은 `paste.html`의 사용 방법·설치 안내에도 들어 있다.
- 확인 필요·번호 필요는 처리함·해당 없음으로 사람이 닫을 때까지 다음 가져오기에도 다시 뜬다(로그 탭이 상태 저장소).

### 11-8. 11.25 개편: 결과 전면 팝업·설치 팝업·범위 읽기 (토미 지시·선택, 구현·푸시 완료 `57bfdd4`)
- 지적: 결과 카드가 시트 DB 위에 깔려 그릇이 섞이고, 블로그/빌리투어 구분이 약하며, 매번 방 전체를 읽는다. 읽기 범위 기본값("마지막 수집 3일 전부터", 위 61줄)은 스펙에만 있고 코드엔 없었다.
- 결정(토미 11.25 선택): 결과는 전면 팝업 + 탭(블로그·빌리투어, 한 줄은 한 탭에만), 상품과 무관한 줄은 `해당 없음 N건` 접힘, 같은 지점·같은 사유 확인 필요는 한 줄로 묶음. 설치 방법은 전면 팝업 3단계 + 안내 그림 3장(`assets/setup-*.svg`, 가짜 데이터). `안 읽힌 건 붙여넣기`는 `결제 알림 직접 붙여넣기`.
- 읽기 범위: 지난 수집의 최신 글 번호보다 오래된 글 30건까지(약 3~5일치, 글 번호 기준이라 시각이 아님). 기준 번호는 등록이 끝난 뒤 `paste.html`이 `nf-commit`으로 북마크에 알려 잔디 주소 localStorage `nf_jandi_commit`에 저장(등록 안 한 건을 건너뛰지 않으려고, 저장 실패 시 다음에도 처음부터 읽을 뿐). `방 처음부터 다시 읽기` 버튼. 결과 화면으로 보내기 클릭은 브라우저 팝업 차단 때문에 필요(추정, 시험 안 함).
- `READER_VERSION` 2: 2대 북마크 재설치 필요. GAS 변경 없음(`complete` 판정은 클라이언트가 `stoppedAtRange`도 완료로 보냄).
- 미확인: 실제 잔디에서 범위 읽기 정지·`nf-commit` 저장, 화면 렌더(팝업 폭·391px). 시험 6개 파일은 통과.
